## 核心工作流技能

### 1. brainstorming - 头脑风暴

**用途**：在创建功能、构建组件、添加新功能或修改行为之前，必须使用此技能进行需求探索。

**触发场景**：
- 开始新的功能开发
- 用户说"我想添加..."、"帮我创建..."
- 需要理解用户真实意图时

**工作流程**：
1. 探索用户的真实需求和意图
2. 明确功能边界和约束
3. 设计实现方案
4. 确认后再开始编码

**价值**：避免做无用功，确保开发方向正确。

---

### 2. writing-plans - 编写计划

**用途**：在有明确需求或规格说明时，编写详细的实施计划。

**触发场景**：
- 收到多步骤任务需求
- 复杂功能需要拆解
- 需要在动手前理清思路

**工作流程**：
1. 分析需求，拆解为可执行的任务
2. 确定任务优先级和依赖关系
3. 生成结构化的计划文档
4. 与用户确认后执行

**价值**：将模糊需求转化为可执行的步骤。

---

### 3. executing-plans - 执行计划

**用途**：在独立会话中执行已编写的实施计划，带审查检查点。

**触发场景**：
- 已有写好的计划文档
- 需要按步骤执行任务
- 需要分阶段验证

**工作流程**：
1. 读取计划文档
2. 按任务逐个执行
3. 每个任务完成后进行验证
4. 记录进度和问题

**价值**：确保计划被完整、准确地执行。

---

### 4. subagent-driven-development - 子代理驱动开发

**用途**：在当前会话中执行具有独立任务的实施计划。

**触发场景**：
- 计划中有多个独立任务
- 任务之间没有强依赖
- 需要快速迭代

**工作流程**：
1. 为每个任务分配独立的子代理
2. 子代理并行执行任务
3. 每个任务完成后进行两阶段审查
4. 合并结果

**价值**：通过并行执行提高效率。

---

### 5. dispatching-parallel-agents - 并行调度代理

**用途**：面对 2 个以上独立任务时，并行调度多个代理。

**触发场景**：
- 多个独立任务需要处理
- 任务之间没有共享状态
- 需要最大化并行效率

**工作流程**：
1. 识别可并行的任务
2. 为每个任务分配代理
3. 收集并整合结果

**价值**：大幅缩短多任务处理时间。

## 开发实践技能

### 6. test-driven-development - 测试驱动开发

**用途**：在编写实现代码之前，先编写测试。

**触发场景**：
- 实现新功能
- 修复 Bug
- 用户提到"红绿重构"、"测试优先"

**工作流程**：
```
RED → GREEN → REFAPEAT
1. RED: 写一个失败的测试
2. GREEN: 写最少代码让测试通过
3. REFACTOR: 重构代码，保持测试通过
4. 重复
```

**核心原则**：
- 测试验证行为，不验证实现
- 垂直切片：一个测试 → 一个实现 → 重复
- 不要水平切片：先写所有测试，再写所有代码

**价值**：确保代码质量，减少回归 Bug。

---

### 7. systematic-debugging - 系统化调试

**用途**：遇到 Bug、测试失败或意外行为时，系统化地诊断问题。

**触发场景**：
- 测试失败
- 运行时错误
- 行为不符合预期

**工作流程**：
1. **收集证据**：读取错误信息、日志、堆栈跟踪
2. **形成假设**：基于证据提出可能的原因
3. **验证假设**：通过最小化测试验证
4. **修复问题**：找到根因后修复
5. **验证修复**：确认问题已解决

**核心原则**：
- 先诊断，后修复
- 不要盲目重试
- 每次只改一个变量

**价值**：快速定位和修复问题，避免浪费时间。

---

### 8. using-git-worktrees - 使用 Git Worktree

**用途**：在需要隔离工作空间时，使用 Git Worktree。

**触发场景**：
- 开始新功能开发
- 需要与当前工作隔离
- 执行实施计划前

**工作流程**：
1. 检查是否已有 worktree
2. 如有需要，创建新的 worktree
3. 在隔离环境中工作
4. 完成后合并回主分支

**价值**：保持工作空间干净，避免干扰。

---

### 9. verification-before-completion - 完成前验证

**用途**：在声称工作完成之前，运行验证命令确认。

**触发场景**：
- 准备提交代码
- 准备创建 PR
- 声称"测试通过"之前

**工作流程**：
1. 运行测试命令
2. 检查退出码和输出
3. 确认无失败
4. 再声称完成

**核心原则**：
- 没有验证证据，不能声称完成
- "应该能通过"不算验证
- 信任但要验证

**价值**：避免虚假的完成声明，确保质量。

## 代码质量技能

### 10. requesting-code-review - 请求代码审查

**用途**：完成任务或实现主要功能后，请求代码审查。

**触发场景**：
- 完成一个功能
- 准备合并前
- 需要外部视角

**工作流程**：
1. 准备审查上下文（改了什么、为什么改）
2. 派发审查子代理
3. 收集反馈
4. 处理审查意见

**价值**：在问题扩散前发现并修复。

---

### 11. receiving-code-review - 接收代码审查

**用途**：收到代码审查反馈时，技术性地评估而非盲目执行。

**触发场景**：
- 收到 PR 评论
- 收到审查建议
- 反馈看起来不清楚或有问题

**工作流程**：
1. 完整阅读反馈，不急于反应
2. 理解要求，用自己的话复述
3. 验证：对照代码库检查
4. 评估：技术上是否合理？
5. 响应：技术性确认或有理有据的反驳

**核心原则**：
- 外部反馈 = 建议，不是命令
- 验证后再实施
- 技术正确性 > 社交舒适度

**价值**：避免盲目修改，保持代码质量。

---

### 12. finishing-a-development-branch - 完成开发分支

**用途**：实现完成、测试通过后，决定如何集成工作。

**触发场景**：
- 所有任务完成
- 测试全部通过
- 需要合并或创建 PR

**工作流程**：
1. 检查工作状态
2. 提供结构化选项（合并、PR、清理）
3. 执行选定的操作
4. 确认完成

**价值**：规范化收尾流程，避免遗漏。

## 协作与审查技能

### 13. using-superpowers - 使用超能力

**用途**：开始任何对话时，建立如何查找和使用技能的规则。

**触发场景**：
- 每次对话开始
- 需要确定使用哪些技能

**核心规则**：
- 即使只有 1% 的可能性适用某技能，也必须调用
- 先检查技能，再回答问题
- 用户指令 > 技能指令 > 默认行为

**价值**：确保技能被正确使用，不遗漏。

## 设计与体验技能

### 14. ui-ux-pro-max - UI/UX 设计智能

**用途**：Web 和移动端的 UI/UX 设计决策。

**包含内容**：
- 50+ 设计风格（玻璃拟态、极简主义、粗野主义等）
- 161 个调色板
- 57 种字体搭配
- 161 种产品类型
- 99 条 UX 指南
- 25 种图表类型
- 10 个技术栈支持

**触发场景**：
- 设计新页面
- 创建或重构 UI 组件
- 选择配色、排版、间距
- 审查 UI 代码
- 优化用户体验

**支持的技术栈**：
- React / Next.js
- Vue / Svelte
- SwiftUI / React Native / Flutter
- Tailwind / shadcn/ui
- HTML/CSS

**价值**：确保 UI 专业、美观、易用。

## 技能使用优先级

当多个技能可能适用时，按以下顺序：

1. **流程技能优先**（brainstorming、debugging）- 决定如何处理任务
2. **实施技能其次**（frontend-design、mcp-builder）- 指导具体执行

**示例**：
- "我们来构建 X" → 先 brainstorming，再实施技能
- "修复这个 Bug" → 先 systematic-debugging，再领域技能

## 注意事项

1. **技能不是可选的**：如果适用，必须使用
2. **用户指令优先**：用户明确说"不用 TDD"时，遵循用户
3. **验证是必须的**：不能声称完成而没有验证证据
4. **技术性反馈**：审查反馈要评估，不要盲目执行
5. **并行优于串行**：独立任务尽量并行处理
